PR for Intent

When the intent itself moves.

The Thread Report catches code that drifts from intent. But sometimes it's the intent that moves — and news travels the thread in both directions. Downward: a decision restates an acceptance criterion, and code written against the old wording is suddenly answering a question no one is asking. Upward: the builder hits ground truth mid-build, and the same PR that changes the code honestly restates the intent it was built against. The durable ID holds through both, so nothing looks broken — which is exactly why the report watches. Intent Changed detects the restatement and tells the two shapes apart by one question: did the code and tests move with the wording? It illuminates; it never blocks.

PR from the Field — the discovery PR

The common, healthy shape. Mid-build, the team instrumented reconcile on real devices and the field pushed back on the spec — in the good direction: propagation lands well under two seconds, every run. The 5s budget in AC-SYNC-01 was looser than the truth. So PR #5 tightens the promise and moves the proof with it, in one diff:

The reviewer reads the intent-diff and the code-diff as one story: the pairing itself is the evidence of coherence. This is what the durable ID buys — AC-SYNC-01 never moves, so the wording and its proof can travel together without the thread ever snapping. Bidirectional traceability isn't a slogan here; it's this PR.

PR from Intent — when the wording moves alone

The alarm state. PR #4 ships the same one-line restatement — 5s → 2s — and nothing else. Maybe product tightened the SLA in the PRD. Maybe an agent "cleaned up" a spec and quietly changed its meaning — in agentic work the spec is the steering wheel, and semantic drift nobody decided is a real failure mode. Either way: the Gate stays green (the ID is unchanged, the named proof still exists and passes), but the proof was written against 5s. It no longer answers for the criterion as it now reads.

It won't rewrite your test; it hands the reviewer a spotlight, not a verdict. Put the two reports side by side and the difference between a coherent discovery and a stale proof is one glance.

Who may move the wording?

Putting Product and Dev in one repo doesn't erase the seam between them — it changes what the seam is made of. A tool boundary (requirements in one system, code in another, news crossing by meeting) becomes a review gate: put the registry under Product's ownership in CODEOWNERS, and no PR that moves an intent's wording merges without a product human's approval. A discovery PR then becomes the ask — "field says 2s; here's the restatement and the proof" — arriving on the diff with the report's was/now attached, instead of in a meeting after the code shipped. And it's the agent defense: a drifted statement must get past both the tripwire (Intent Changed) and the lock (CODEOWNERS). Who types the words stays separate from who approves them — drafts are cheap now; the durable ID keeps the approval about wording, never renumbering.

How sharp the pointer gets

A restatement's blast radius depends on how much the machine can prove. SpecAssay never guesses past that line — it grades the re-confirm hint into three tiers, sharpest first:

1

Pinpointed — the old value still lives in a carrier

test_sync.py:37 ⚠ still contains the old 5s

When the old concrete value (a number-with-unit, a quoted string, an ALL-CAPS constant) is still present verbatim in the code or a test that carries the intent, the report points straight at it. PR #4's case — the strongest signal it can give: here is the exact line that still encodes what you just changed.

2

Value gone — changed, but not found verbatim

Value 5s → 2s changed, but not found verbatim in the code or tests — re-confirm by reading.
sync.py:51 · test_sync.py:18

A value moved, but the old one isn't sitting in any carrier verbatim — on a discovery PR because the carriers were updated in the same diff (PR #5's case), elsewhere maybe because it was abstracted behind a constant. The machine can't pin a line, so it says so plainly and lists the carriers to re-read. Honest about what it doesn't know.

3

Prose — no literal value to pin down

Prose change — no literal value to pin down; re-confirm the code and its test by reading them against the new wording.
sync.py:51 · test_sync.py:18

The wording changed in meaning, not in any greppable value — "ordered by relevance" becomes "ordered by recency." There's nothing to search for, so the machine doesn't pretend. It flags the criterion, lists the carriers, and asks a human to read them against the new sentence. The default, and the most common.

Why re-confirm, and never block

Restating an intent is legitimate, routine work — requirements tighten, ground truth pushes back, product learns. The machine has no way to know whether the existing code still satisfies the new sentence; that's a human judgement. So Intent Changed sits squarely on the illuminate rung — the same doctrine that governs "off thread":

  • Illuminate — always on

    The Intent Changed section above. It surfaces the restated criterion and its blast radius, and renders no verdict on whether the code still holds.

  • Affirm — the human tick

    Re-confirmation is a person's call: read the carriers, decide they still answer for the new wording, and merge. Set intent_ack: required and the report grows a checkbox a human must tick before merge. Note where it bites: on a PR from Intent the tick is a real stop-and-look; on a discovery PR the re-confirmation is already sitting in the diff.

  • Refuse — not here

    The Gate blocks only what it can prove is a defect: a silent acceptance-criterion gap, an invented ID, exact-set drift. A restatement is none of those — the ID is durable, the proof is present. So it never earns a refusal.

A durable ID promises the wording can change without the thread snapping. Intent Changed is how that promise stays honest — in both directions: the field may correct the intent, and the intent may move ahead of the field, but neither happens silently.

And it stays a comment. SpecAssay posts beside your PR; it never edits the criterion, the code, or the test. The diff is the record; the Thread Report is the reading glass.
