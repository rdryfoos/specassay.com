PR for Intent

When the intent itself moves.

The Thread Report catches code that drifts from intent. Sometimes it's the intent that moves — in either direction. Product tightens a requirement and the code hasn't caught up yet. Or a builder learns something in the field, and the spec needs to catch up with reality. Either way the durable ID holds and the Gate stays green — nothing looks broken. So the report watches for it: Intent Changed spots every rewording and asks one question — did the code and tests move with it? It illuminates; it never blocks.

Who may move the wording?

Product and Dev share the repo, but the wording still belongs to Product — and that's one line of GitHub config. Put the PRD in CODEOWNERS, and any PR touching an intent's wording waits for Product's approval. Watch what that does to the discovery PR: it becomes the ask. Dev opens it — new wording, updated proof, report attached — and Product reviews right on the diff, instead of in a meeting after the code shipped. It also stops a drifting agent: a reworded spec can't merge until a person approves it.

The same works in reverse. When Product rewrites a requirement, Dev's files don't change, so no file-ownership rule will ask Dev anything — but Dev's tests now owe an update. That's what the intent_ack checkbox is for: before the PR merges, someone from the build side ticks that the code and tests were checked against the new wording. CODEOWNERS asks about the files a PR changes; intent_ack asks about the work it creates. Two gates, one each:

And if the tick can't honestly be given — the test really is out of date — there are two ordinary ways forward. Dev pushes the test update onto the same PR, and the report shows (updated here). Or the team files the follow-up task, and the row rides as tracked-debt until it's paid. Either way, nothing merges hidden.

How sharp the pointer gets

How hard the report leans depends on what it can prove. Three tiers, sharpest first:

1

Pinpointed — the old value still lives in a carrier

test_sync.py:37 ⚠ still contains the old 5s

The old value — a number, a quoted string, a constant — still sits in the code or a test, and the report points at the exact line. PR #4's case, and the sharpest hint it can give: here is the line that still says what you just changed.

2

Value gone — changed, but not found verbatim

Value 5s → 2s changed, but not found verbatim in the code or tests — re-confirm by reading.
sync.py:51 · test_sync.py:18 (updated here)

The value changed, but the old one isn't in the code anymore — on a discovery PR because it was just updated (PR #5's case). Nothing to point at, so the report says so and lists what to re-read.

3

Prose — no literal value to pin down

Prose change — no literal value to pin down; re-confirm the code and its test by reading them against the new wording.
sync.py:51 · test_sync.py:18

The wording changed in meaning, not in any searchable value — "ordered by relevance" becomes "ordered by recency." The report doesn't pretend otherwise: it lists the code and the test and asks a human to read them against the new sentence. The most common case.

Why re-confirm, and never block

Rewording an intent is normal work — requirements tighten, reality pushes back, product learns. Whether the existing code still satisfies a new sentence is a human judgement, so the report never blocks on it:

  • Illuminate — always on

    The Intent Changed section above: what was reworded, and which code and tests to check. No verdict.

  • Affirm — the human tick

    Set intent_ack: required and the report adds a checkbox a human must tick before merge. It matters most when the wording moved alone; on a discovery PR the answer is already in the diff.

  • Refuse — not here

    The Gate blocks only what it can prove is a defect — a silent gap, an invented ID, registry drift. A rewording is none of those, so it never earns a refusal.

A durable ID means the wording can change without the thread snapping. Intent Changed keeps that honest — in both directions, and never silently.

And it stays a comment. SpecAssay posts beside your PR; it never edits the wording, the code, or the test. The diff is the record; the Thread Report is the reading glass.
