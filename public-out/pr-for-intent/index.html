PR for Intent

When the intent itself moves.

The Thread Report catches code that drifts from intent. But sometimes it's the intent that moves: someone rewrites an acceptance criterion, and the code and tests written against the old wording are suddenly answering a question no one is asking. The durable ID is stable, so nothing looks broken — a green check would wave it straight through. Intent Changed is the section that catches exactly this. It flags the restated criterion and points at the code and tests that now owe a re-confirmation. It illuminates; it never blocks.

The pull request

This walkthrough is a real PR on the bundled example app. Product tightened the offline-sync SLA — a change made offline should now appear on a second device within 2s of reconnect, down from 5s. That's one line in the PRD: the acceptance criterion AC-SYNC-01 gets restated. The ID doesn't move; its meaning does.

examples/example-app/PRD.mdAC-SYNC-01 restated: within 5s → within 2sintent moved

The Gate stays green: the ID is unchanged, the @covers mark still holds, and the named proof still exists and still passes. On its own, that green check would pass this PR as done. But the proof was written against 5s — it no longer answers for the criterion as it now reads. That gap between a passing test and a moved requirement is exactly what Intent Changed exists to surface.

The briefing it pins to the PR

1
🧵 Thread Report
🟢 Golden Thread intact

Nothing broke. A restatement isn't a defect — the ID is stable, the proof is present, the thread still holds end to end. So the header reads intact, and everything that follows is a reading, not a refusal. This is the illuminate rung doing its job: surface what's decision-relevant, render no verdict.

2

Intent Changed

⚠️ 1 intent was restated — its wording moved under the code and tests written against the old text. Re-confirm each still satisfies the new statement.
AC-SYNC-01 — restated
was: … appears on a second device within 5s of reconnect.
now: … appears on a second device within 2s of reconnect.
re-confirm:
sync.py:51 test_sync.py:37 ⚠ still contains the old 5s

The restatement is detected, not guessed. SpecAssay diffs the base registry against the PR-head registry, whitespace-insensitive — so a reflow or a typo fix is ignored, but a substantive reword of a criterion's own statement counts. Here AC-SYNC-01's wording moved from 5s to 2s, and the section prints the before and after so the reviewer reads the change in the criterion's own words, not just a diff hunk.

3
test_sync.py:37 ⚠ still contains the old 5s

This is the catch. The old value 5s was a concrete token — a number the machine can grep for. It's gone from the statement, but it still lives in the proof: test_sync.py line 37 asserts elapsed < 5.0 under a comment that reads within 5s. The test passes, the thread is green — but it's proving the old requirement. SpecAssay names the exact file and line, straight to the diff, and stops. It won't rewrite your test; it hands the reviewer a spotlight, not a verdict.

How sharp the pointer gets

A restatement's blast radius depends on how much the machine can prove. SpecAssay never guesses past that line — it grades the re-confirm hint into three tiers, sharpest first:

1

Pinpointed — the old value still lives in a carrier

test_sync.py:37 ⚠ still contains the old 5s

When the old concrete value (a number-with-unit, a quoted string, an ALL-CAPS constant) is still present verbatim in the code or a test that carries the intent, the report points straight at it. This is PR #4's case — the strongest signal it can give: here is the exact line that still encodes what you just changed.

2

Value gone — changed, but not found verbatim

Value 5s → 2s changed, but not found verbatim in the code or tests — re-confirm by reading.
sync.py:51 · test_sync.py:37

A value moved, but the old one isn't sitting in any carrier verbatim — maybe it was abstracted behind a constant, maybe the logic never hard-coded it. The machine can't pin a line, so it says so plainly and lists the carriers to re-read. Honest about what it doesn't know.

3

Prose — no literal value to pin down

Prose change — no literal value to pin down; re-confirm the code and its test by reading them against the new wording.
sync.py:51 · test_sync.py:37

The wording changed in meaning, not in any greppable value — "ordered by relevance" becomes "ordered by recency." There's nothing to search for, so the machine doesn't pretend. It flags the criterion, lists the carriers, and asks a human to read them against the new sentence. The default, and the most common.

Why re-confirm, and never block

Restating an intent is legitimate, routine work — requirements tighten, wording sharpens, product learns. The machine has no way to know whether the existing code still satisfies the new sentence; that's a human judgement. So Intent Changed sits squarely on the illuminate rung — the same doctrine that governs "off thread":

  • Illuminate — always on

    The Intent Changed section above. It surfaces the restated criterion and its blast radius, and renders no verdict on whether the code still holds.

  • Affirm — the human tick

    Re-confirmation is a person's call: read the carriers, decide they still answer for the new wording, and merge. The report makes that decision cheap and visible — it never makes it for you.

  • Refuse — not here

    The Gate blocks only what it can prove is a defect: a silent acceptance-criterion gap, an invented ID, exact-set drift. A restatement is none of those — the ID is durable, the proof is present. So it never earns a refusal.

A durable ID promises the wording can change without the thread snapping. Intent Changed is how that promise stays honest — it makes sure the number didn't move while the proof stood still.

And it stays a comment. SpecAssay posts beside your PR; it never edits the criterion, the code, or the test. The diff is the record; the Thread Report is the reading glass.
